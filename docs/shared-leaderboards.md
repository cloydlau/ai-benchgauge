## 并发采集与旧价格接口补齐（2026-10-31）

同一子榜的采集资格由 OSS coordination.log 的追加位置 CAS 原子争用，跨用户、FC 冷启动和多实例共用；并非进程内布尔锁。新旧客户端使用同一协调键，未获资格只读快照，重复刷新不延长冷却。回传和后端兜底也先争用并消费同一令牌，最多一方提交；协调存储失败时不允许接触原站。客户端只有得到资格后才用实际 GET 探测并下载，不单独探测原站。

本轮修复旧版 OpenRouter 价格三个入口此前仅有进程内十分钟缓存的问题：现在走与 client-first 相同的持久化资格与三十分钟窗口，继续保留目录及榜单两种响应结构。后端兜底在慢存储/缓存读取后、请求原站前再次检查 90 秒资格期限，避免越过为下一轮预留的窗口。

三十分钟指每个评测/价格子榜的一轮采集，其他用户不能另起一轮；一轮含一次用户网络采集及失败时的一次后端兜底，Arena/Epoch 领域榜的一轮可能包含多个固定资源请求，并非整站每三十分钟只允许一个 HTTP 请求。公开用量继续沿用既有每日成功周期及失败退避。42 项相关定向回归通过，包含五类榜单各 100 个冷实例抢资格、新旧接口竞争、100 个回传/兜底竞争、慢存储过期、旧价格 HTTP 冷实例及协调故障；完整门禁和发布交由现有 Calmmit 流程，不能将本地定向通过称为线上已生效。

## 用户网络优先协议（2026-10-31）

新客户端的 `POST /v1/boards/{kind}/refresh` 携带 `X-BenchGauge-Acquisition: client-first`。先展示本地及共享缓存；获得资格的客户端按服务端固定资源清单请求原始数据。GET 本身同时完成连通性探测和下载，不额外 HEAD、不在启动时扫描所有榜。各榜沿用按需刷新触发，但同一原始资源组合共用采集资格；未获资格只读共享快照。

`grant.acquisition.resources` 包含固定 URL、类型、大小上限及可选资源；Arena 先获取官方元数据，再用其中 40 位 SHA 请求固定修订的 Parquet。客户端通过 `/acquire` 上传 Base64 原始资源，后端复用官方解析器校验和拟合，客户端不提交排名、时间或拟合结果。AA 页面、Epoch 综合 CSV、三个 Epoch 领域榜、所有 Arena 子榜、Vercel、腾讯云文档和 OpenRouter 公开价格均使用此路径。OpenRouter 用量需要服务端密钥，仍仅在后端采集，不下发密钥。

用户网络不可达、微信合法域名限制、源站返回拦截页或上传被拒时，客户端用同一个令牌请求 `/fallback`，由后端现有直连或采集器兜底。后端在发起源站请求前 CAS 消费授权；并发回退、重放及其他客户端不能重复采集，不另领资格、不重置冷却。资格 90 秒；评测榜与价格沿用 30 分钟刷新窗口，一个窗口最多一次客户端采集和一次后端兜底；公开用量成功后沿用每日间隔，客户端中断或两路失败沿用十分钟退避恢复。两条路径均失败则保留原快照；上传响应丢失时再读共享缓存，避免遗漏已经提交的数据。

保留旧协议及旧版客户端兼容；下述 Arena “仅后端” 和 HTML “失败保留旧缓存” 的记录描述旧协议。新协议继续拒绝 Arena 官网 HTML，改为允许经过校验的官方数据集原始资源。

## 旧版客户端流程（兼容保留）

1. `POST /v1/boards/{kind}/refresh` 返回共享快照及可选的更新资格。
2. 没有更新资格时，直接显示共享快照，禁止向原站发起请求。首次快照尚未产生时，只短暂轮询共享读取接口。
3. 拿到资格的客户端先显示 FC 返回的缓存，再在后台请求该榜单固定的原站地址、校验并上传 HTML。贡献流程总时限为 30 秒（原站请求 20 秒、上传请求 10 秒，受总时限约束）；资格仍有 90 秒有效期。服务端重新解析数据；客户端不直接上传分数表或更新时间。
4. 上传成功后，原位更新为服务端确认的快照。原站被屏蔽、解析失败、上传失败或贡献超时时，继续显示共享旧快照；共享服务不可用时，保留本地缓存。刷新期间不清空表格、不遮挡交互；手机保留榜单标题右上角的小提示。

`GET /v1/boards/{kind}` 用于读取共享快照（用量来源有自己的服务端更新间隔）。小程序仍通过该接口取得服务器已有的快照；Apple 和 Windows 的刷新通过 `POST .../refresh` 申请更新。Windows 手动刷新直接进入共享的每榜任务，不在此前另发一次缓存请求，避免自动刷新完成后又发起重复刷新；Apple 两端通过 fetcher 的缓存回调立即呈现并保存，独立来源完成后也立即更新。

### 客户端刷新触发（2026-10-24）

四端均不通过周期计时器刷新榜单。首次进入或切换到某榜时，只检查该榜：有 `sourceUpdatedAt` 时按发布时间计算，否则按 `fetchedAt` 计算；达到 24 小时（含边界）或没有缓存才自动请求。小程序和手机仅检查当前选中的来源，平板与桌面多榜视图逐张检查可见来源；其他分类和隐藏来源不参与。停留在同一榜、回到前台或调整筛选不触发自动请求。

自动刷新与手动下拉／点击刷新共享每榜在途任务；手动操作立即加入已有任务并等待其结束，不另排第二次更新。没有在途任务时，手动刷新不受客户端的 24 小时判断和自动退避限制。自动请求开始后 5 分钟内不因反复进入再次请求，避免上游发布日期没变或请求失败时密集重试；退避到期本身不安排刷新，仍需下一次进入榜单。服务端按来源覆盖范围的共享限频继续适用，手动操作不能绕过它。失败保留原快照与原时间。订阅余量、账户和模型资料的独立计时流程不属于榜单刷新。

更新资格在所有用户、所有 FC 实例之间共享；按本页来源覆盖表的采集组限频，单榜资源仍独立。资格有效期结束后，再等待 30 分钟才允许下一次更新，因此实际资格间隔为 31 分 30 秒。失败也占用这一轮，手动刷新不能绕过限制。被拒绝的请求不延长等待期。

原站提供的 `sourceUpdatedAt` 与成功拉取时间 `fetchedAt` 分别保留；读取缓存不修改任何时间。本地数据比共享快照更新时，也不会被共享旧数据覆盖。现有相对时间、原站更新时间提示直接使用这些字段。

## 模型开放状态

快照条目可选携带 `openness`（`open` / `closed`）。Apple 本地解析器与 FC 解析器采用相同规则：Artificial Analysis 的 `isOpenWeights` 布尔值或媒体榜 `openWeightsUrl`；Arena 的 `license`。`Proprietary` 为闭源，已识别的公开权重许可证为开源；受限社区、研究或非商业许可证也按源站的公开权重分类，并不代表无使用限制或 OSI 认证。未识别的许可证、缺字段、旧缓存，以及公司聚合行保持未提供状态，界面显示 `—`。当前 Artificial Analysis 编程智能体榜没有这些字段，不能仅凭厂商名称判断。

编程榜缺少开放状态时，共享服务在读取时复用现存文本榜及 Arena 编程榜中同一模型的明确分类。只匹配完整模型 ID 或去除推理设置后的完整模型名称；代理名称不参与模型匹配，参数规模、日期和版本保持区分。已有明确分类优先，匹配不到或证据冲突时仍显示 `—`。不按厂商猜测，也不将开源代理工具等同于开源模型。

状态随正常榜单刷新或贡献自动更新并保存到 OSS；编程榜的补齐只影响返回数据，不写回推断结果，也不改动分数、排名、更新时间或全局刷新限频，不额外请求原站。旧快照也可立即使用已保存的模型资料。中文列名为「源码」，英文为 `Source`；值为「开源 / 闭源」或 `Open / Closed`。

## 存储和并发

每张榜单使用两个私有对象：

- `benchgauge/{kind}/latest.json`：唯一一份排行榜快照，原子覆盖。
- `benchgauge/{采集协调键}/coordination.log`：更新资格的少量协调元数据，不保存 HTML 或排行榜历史。同组复用首个成员原有协调键；迁移期读取其他成员旧日志以保留冷却。

协调对象使用 OSS `AppendObject` 的位置前置条件：并发实例只有一个能在同一位置追加成功。读操作通常读取日志末尾 2 KB；如果旧版的末条记录超过此长度，则逐步扩展读取至最多 64 KB，并保持首次读取的追加位置不变。资格只保存令牌的 SHA-256 摘要。上传先原子消费资格，重放或并发上传只有一个能发布。无数据库、进程内锁或固定单实例假设。

协调日志会增长，每次成功发放或消费资格追加一行。它不能随意删除或设置自动过期，否则可能重置限频窗口。若以后需要整理，先暂停发放资格并等待至少 31 分 30 秒，再重置协调对象；排行榜快照保持不动。

必须使用未开启过版本控制的 Bucket，并保证生命周期规则不会删除 `benchgauge/` 下的任何对象。对象保持私有；用户通过 FC 读取，不能直接访问或写入 OSS。

## 部署

运行 `npm ci --prefix fc --include=optional --ignore-scripts` 安装部署依赖。在被 Git 忽略的 `.benchgauge-cloud.local.json` 中配置：

```json
{
  "region": "cn-shenzhen",
  "functionName": "ai-benchgauge",
  "arenaCollector": true,
  "bucket": "ai-benchgauge",
  "runtimeCredentialsFunction": "weaveo",
  "runtimeIdentityName": "limphase-runtime",
  "credentialsFile": "/absolute/path/to/private-cloud.env"
}
```

也可从进程环境变量读取 `ALIBABA_CLOUD_ACCESS_KEY_ID`、`ALIBABA_CLOUD_ACCESS_KEY_SECRET`。配置必须包含已有专用 `bucket`，以及以下一种已有运行身份：

- `runtimeCredentialsFunction` 加 `runtimeIdentityName`：从本账号指定 FC 函数的运行环境复用云凭证，在内存中校验 STS 身份后传给新函数；只转移阿里云凭证，不复制其他供应商密钥。服务端明确使用环境凭证，忽略公共请求中的凭证头。
- `roleArn`：指定已准备好的 FC 执行角色，使用 FC 注入的临时凭证。

`proxy` 可指定本机 HTTP 代理。本机部署凭据从 weaveo 复用至被忽略、权限为 `0600` 的 `.env.local`；这些是部署用户凭据，与运行用户区分。不要提交本机配置或把密钥填入客户端。

当前本机配置使用用户创建的 `ai-benchgauge` 桶、`runtimeCredentialsFunction: "weaveo"`、`runtimeIdentityName: "limphase-runtime"`。STS 已确认 `limphase-runtime` 是本账号的 RAM 用户，Weaveo 使用它的运行凭证。部署脚本不创建 Bucket、RAM 角色或权限策略，也不要求 RAM 管理权限。运行身份需要读取桶配置，并具有快照读取、覆盖写入和协调对象追加权限。

开发入口自动监听共享服务和部署配置。源码静默 60 秒且本仓库的 AI 任务结束后，先运行项目完整测试及覆盖率门禁和服务端测试；通过后打包并依次更新新加坡采集器、深圳主函数的代码。自动部署保留现有函数配置、密钥、触发器和 OSS 数据，并备份发布前的代码包。发布后下载两个线上代码包核对哈希，再检查采集器认证和主服务的榜单读取；全部通过才写入 `work/shared-fc-auto/success.json`。源码、测试输入、部署配置或线上函数在途中发生变化时停止本轮，等待新一轮；失败及部分发布不会记录为成功。日志由开发入口输出，备份和候选包保存在被忽略的 `work/`。暂时关闭本机自动监听可设置 `SHARED_FC_AUTODEPLOY=0`。

```sh
node Scripts/deploy-shared-leaderboards.mjs --plan
node Scripts/deploy-shared-leaderboards.mjs --package
node Scripts/deploy-shared-leaderboards.mjs
```

部署使用 `custom.debian10` 的 Node.js 20，512 MB / 0.25 vCPU、512 MB 临时磁盘，实例并发 8、请求超时 30 秒，按需启动。临时磁盘只供运行程序，不存放共享快照。函数通过深圳 OSS 内网地址访问存储。部署脚本先运行服务端测试，再打包生产依赖；不会覆盖无关函数。部署回执保存在被忽略的 `work/shared-leaderboards/deployment.json`。ZIP、应用和接口响应均不包含云密钥；运行凭证仅存放在 FC 的运行配置中。

`arenaCollector: true` 同时部署新加坡的专用采集函数，解决深圳直连 Hugging Face 和 OpenRouter 超时。它没有 OSS/云凭据，仅接受四个 Arena 固定路径、models.dev 元数据和 OpenRouter 用量路由，均须携带专用随机令牌。用量路由还须携带主函数转发的 OpenRouter 认证头，Key 只在请求内存中使用，不在采集函数配置中保存。令牌保存在被忽略的 `work/shared-leaderboards/arena-collector-token`（0600）及运行环境，重部署复用；丢失后重新生成并同时更新两端。部署后验证未认证访问为 403、各来源完整链路及原共享读取地址。

部署后先验证读取接口；Arena 通过刷新接口读取官方数据集，其他来源使用更新资格从原站填充。确认读写链路可用后，设置 `Sources/LeaderboardKit/SharedLeaderboardConfiguration.swift` 的 `bundledEndpoint`，再构建应用。iOS、macOS、Windows 引用同一个 Swift 配置。开发调试也可设置 `BENCHGAUGE_SHARED_ENDPOINT`；配置了共享服务后，服务失败不能回退到无资格的原站请求。

## 客户端贡献的边界

Arena 禁止官网 HTML 贡献；新协议仅接受官方数据集原始资源。以下边界适用于所有客户端原始数据贡献。公开接口的贡献资格不等于原站来源证明。服务端校验来源类型、完整记录数量、字段和数值范围、原站时间不倒退、令牌有效期及一次性使用，并过滤任意外部图片地址；但无法仅凭客户端上传的 HTML、CSV、JSON 或 Parquet，证明它确实来自原站的 HTTPS 响应。恶意客户端仍可能伪造符合结构的 HTML。若需要防范这种行为，后续必须加入可信贡献者认证、设备证明或独立来源验证，不能把格式校验描述为原站真实性校验。

## 动态厂商国家资料

每次共享榜单刷新（包括源站刷新尚在限流期间）和新榜单提交时，按统一厂商 key 识别缺少国家资料的厂商。已知厂商的新型号复用同一份资料；国家指模型开发商总部，编码代理跟随主模型厂商，公司榜继承该厂商资料。

## 排名变化

2026-10-30 线上修复：线上函数此前未包含 `withRankChanges`，因此即使客户端更新了榜单，也不会收到名次变化。基于部署前的实际函数代码包，只在 `domain.mjs` 与 `service.mjs` 中加入现有排名比较及公司投影，更新函数代码，保留其配置、凭据、触发器和 OSS 榜单。部署前代码包、精确修复包、校验值和回执保存在忽略目录 `work/rank-live-investigation/`；云端临时上传对象已删除。部署后核对代码包 SHA-256、四条采集写入路径和函数配置一致。

修复包针对实际线上依赖通过 6 项排名变化回归，覆盖模型升降与新入榜、重复抓取、歧义身份、公司排名、四类 API 采集和写入失败。线上 Arena 文本与编程榜均成功执行正常刷新，返回的上游发布日期仍为 2026-10-28，未出现可确认的新排名变化，因此尚未通过真实升降数据做线上端到端验证。此前未保存的历史名次不能追溯；以后只有来源榜单实际发生名次变化才会产生标记，重复刷新不会凭空产生变化。

每次成功采集后，服务端在替换旧快照前计算 `rankChange`（`delta = 旧名次 - 新名次`，正数上升、负数下降；首次入榜为 `isNew: true`）。无可用旧榜单时不标记全榜为新。模型按稳定 ID 匹配，无 ID 时按名称和机构匹配；Arena 的临时排名后缀不参与身份，重复身份无法唯一对应时不猜测名次。公司按各自榜内聚合名次独立比较，结果存入模型行的 `companyRankChange`，公司投影读取该字段，不继承旗舰模型的升降。

模型和公司各自按稳定身份与名次序列比较，只有对应序列的成员或名次变化才开始该类的新一轮比较。仅分数、用量、名称、抓取时间、投票数或补充资料变化时保留该类上一轮标记；即使用量份额变化造成公司重排，也不清空未重排的模型标记。新一轮名次变化中持平的条目不展示升降，离榜条目不继续展示。内容更新时间仍独立记录分数、成本等内容变化，不能据该时间推断名次也发生了变化。比较结果与新榜单写入同一个快照，写入失败继续保留旧榜单。各端、离线缓存和图片导出消费同一份结果，筛选不重新定义原榜名次变化。旧快照不含这些可选字段仍可正常读取。
